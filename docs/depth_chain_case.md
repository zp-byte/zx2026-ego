## 3. 改动清单

### 3.1 新增 `src/arena_sensor/scripts/depth_cloud_node.py`
把深度图反投影成与 `lidar_node.py` 逐字段同契约的点云。

**反投影（精确闭式）**：渲染器取 `d=[u,v,1]`、存 `1/|d|`，命中时
`Z = t·(1/|d|)`（沿光轴分量，**非斜距**）⇒ `t = Z·|d|` ⇒ 命中点
`= o + Z·d`：

```
P_world = pos + Z·(u·rgt + v·dwn + fwd)
u=(col−cx)/fx,  v=(row−cy)/fy,  Z=mm/1000
(rgt,dwn,fwd) = cam_basis(yaw, cam_pitch_deg)
```

**必须 yaw-only**：渲染时 `cam_basis` 只吃 yaw，roll/pitch 已被丢弃。改用完整
odom 四元数 = 施加一个图像从未经历过的旋转，每点按当时 roll/pitch 系统性偏移，
**而点云自身仍自洽、看起来完全合理**——是查不出来的错。

**哨兵雷（本节点的核心正确性）**：`depth_sim_node.py:359-362` 把**无命中**像素
写 `Z = t_max = max_range`（=10000 毫米哨兵），而无效化判据是 `Z > t_max`
（**严格大于**）故**恰等于 t_max 不被清零**。⇒ 毫米域里 **`0` 与
`≥ max_range*1000` 都是「无效」**，只有 `0 < mm < 10000` 才是测量。
漏掉上界的后果是结构性的：pitch=0 的前视相机，无命中射线反投影后落在
z≈0.85，**正好砸进 nav 的占用带 [0.70, 2.60]**，形成一座跟着机头走的 10 m
幻影墙。且 `lidar_node` 对未命中是 `continue`（根本不产点），发哨兵点也是契约违背。

**降采样 stride=12**：见 §4.1 定标表。含 `max_points` 兜底、`decim` 整数抽帧、
odom 断流停发、**绝不发空云**（空云会把 nav 的记忆窗挤掉＝主动销毁信息）。

### 3.4 修的两个 bug

**① `depth_sim_node.py:460` CameraInfo.D 序列化（arena 原样带来的潜伏缺陷）**
```python
info.D = Float64MultiArray(data=[0.0] * 5)   # ★ CameraInfo.D 是 float64[]
```
失败点在 **TCP 建连**（`_tcp_server_callback → add_connection → serialize`），
即 **`camera_info` 从未成功连上过任何订阅者**；`image_raw` 是另一条连接不受影响
⇒ 症状是「图像正常但 K 无人收到」。深度默认关时无人消费故潜伏至今。
修复：`info.D = [0.0] * 5`（K/R/P 早已是 list，只有 D 错）。

**② 发布率混叠（我自己第一版的错）**：初版用时间门限 `1/rate_hz` 配 15Hz 图像源
⇒ 相拍成 **7.5Hz**（实测 min 0.116/max 0.152s），而注释宣称 ~10Hz。
**数值对不上就是隐患**。改为**整数抽帧** `decim=2`：发布率 = fps/decim **精确 7.5Hz**，
且在 gz 后端的仿真时钟下行为不随 RTF 漂。

**③ 仪表化（顺手，防止「沉默即通过」）**：K 交叉校验原先一致时静默 ⇒
静默既可能是通过、也可能是回调根本没跑（本次踩的就是后者）。改为一致时也打
INFO「两源对质通过」，把沉默变成**正面证据**。

#### ★ 头号定谳：任务预算是**墙上时钟**，深度链的算力代价被换算成任务时间

`stage_controller_node.py` 用 `rospy.get_time()` 计 P4 超时（`:94-104`），
`phase_start` 在全体起飞完成进 P4 时赋值（`:65`）。而 **py 后端从不设
`/use_sim_time` rosparam**（只有 `arena_world_gazebo/launch/gazebo.launch:17`
设了），`world_node` 那个 `/clock` 话题没人读 ⇒ **全图跑墙钟**。

两条独立证据：

1. **rosout 时间戳 == 真实墙钟**：`rosout.log` 末行 `1791368122.610849380`，
   `stat` mtime `2026-10-07 18:15:22.610574169 +0800` —— **逐毫秒吻合**。
2. **超时算术对双臂闭合**：

   | 臂 | P4 进入 | 超时触发 | Δ |
   |---|---|---|---|
   | lidar | 1791368260.709 | 1791368440.716 | **180.01 s** |
   | depth | 1791367930.171 | 1791368110.319 | **180.15 s** |

⇒ 同样的 180 秒墙钟，两臂买到的**仿真飞行时间**：

```
lidar:  180 × 0.918 ≈ 165 s     ← 刚好够落 3 架，过 PASS 线
depth:  180 × 0.661 ≈ 119 s     ← 少 46 s，landed = 0
```

**「深度的 RTF 代价」和「任务跑不完」是同一件事，不是两件事。**
arena 基线本身在时限上就是紧的（lidar 臂 `full_completion: False`、
drone3 从未 match、drone0/4 还在返航中闸刀就落了）——**RTF 是这个任务的
一等约束，不是环境读数**。这与既有定谳「RTF 是判据⓪」方向一致，
但此处更进一步：**它还是因果链上的一环**。

而空间密度由**另一个**参数 `stride`（默认 12）决定，本次未动。

```
旧: 渲染 15 Hz，发每 2 帧 → 7.5 Hz      ← 白渲染一半（那半帧渲完就丢）
新: 渲染 7.5 Hz，发每 1 帧 → 7.5 Hz     ← 渲染成本减半，交付流同率同密度
```

⇒ **两个深度臂交付给 nav 的感知流同率、同密度、同内参、同哨兵规则**
（每 ~133 ms 一帧新渲染、每帧约 400–670 点、`stride=12`）
⇒ **唯一变量是渲染占用的 CPU 与由此决定的 RTF**。
（诚实边界：**不是逐字节等价** —— 渲染时刻从 15 Hz 网格挪到 7.5 Hz 网格，
每帧的点集与旧臂并不逐点相同；可比的是**率、密度、契约**这三项，均已实测。）

### 4.8 撞点几何法证：**撞的全是它当拍看不见的树**（免改码，2026-10-07）

**仪器**：撞点行本身就带遥测，无需改一行码，也无需重跑。
`nav_node._on_collision`（`:818`）在打 marker 前调 `_closing_speed()`，后者遍历
`self.cloud` 取「撞拍瞬间本机点云里最近点」的距离：

```
nav_node: drone %d collision marker at (%.1f,%.1f) cell (%d,%d) close=%.2f clr=%.2f
                                                                  ↑闭合速度   ↑最近点距离
```

**判据（闭式，不依赖航向）**：物理接触 ⇒ 被撞表面距机心 ≈ `drone_radius = 0.35 m`。
若该表面在点云里有点，`clr` 就该 ≈0.35；`clr` 很大只能意味着**那东西不在点云里**。
`self.cloud` 的定义已在源码核实 = **最近一帧**（`nav_node.py:514`「最近一帧点云」；
`_on_cloud:894` 仅在 `cloud_mem_frames>1` 时聚成最近 N 帧）⇒ **它量的正是反应层当拍的输入**。

**两个免改码的仪器**（均落盘可复算）：

### 4.9 根因定谳：**导航相机整局只朝东**——航向冻死在初值 0（2026-10-07）

**一句话**：`/drone_<id>/vel_cmd` 的契约里 `angular.z` 是**偏航速率**，而 `nav_node`
是这个话题**唯一**的写者，却**从来没有赋过 `angular.z`** —— 于是偏航速率恒等于 0，
每架机的 `yaw` 从起飞到落地都冻在 `reset` 时写的 **0.0 rad（正东 +x）**。
深度臂的导航云源是一台**按 `odom_yaw` 渲染的前视相机** ⇒ 它的感知整局只有一个
**朝东的 87°×58° 楔形**，无论飞机飞向哪里。

§4.8 的 26 起盲撞（贴着障碍面撞、而点云最近点在 1.81–5.92 m 外）不是「FOV 窄」，
是**相机根本没朝行进方向看**。当时列的四个候选（`min_range=0.2` 近距致盲、
遮挡、机体自遮挡、`stride=12` 漏采样）**全部否**。

#### 与实测吻合的三处（独立佐证，非同一来源）

1. **场地几何**：投放点 x ≈ **+27**（东）、机坪 x ≈ **−28**（西）
   ⇒ 回程是**倒着飞**，相机仍朝东；d5 那 4 起贴网滑行在 x ≈ −22.8、网 #207 的

   ⇒ 最近点只能在老远处。这正是 §4.8 测到的形态。
3. **两臂分布**：深度臂 Σcol **26.7** vs 雷达 **2.0**（§4.7 矩阵，13.3×），

#### 为什么这条改动值得做（时间账）

预算**没有余量**：`time_limit_s: 180`（`competition_rules.yaml:6`），
depth r1/r2 与 lidar r1 **三局全部精确在 180.0–180.1 s 被 `stage_controller`
强制封卷**、`full_completion: False` 恒真 ⇒ 分数全是「180 秒内做了多少」的吞吐量。
而**每起碰撞本身也吃这块时间**：`bounce_dt 1.0 s` 弹开 + `cooldown_dt 2.0 s`
零速冻结 ≈ **3 s 非生产时间**（`world_node.py:425-428`）；depth r1 逐机 d2 六撞
≈ 18 s、d3/d5 各五撞 ≈ 15 s（占预算 8–10%）。
**「转向花掉的时间 vs 碰撞省下的时间」孰大，就是本 A/B 要回答的那个问题。**

#### 修复（`heading_align`，默认 off）

5. **gz 后端未覆盖**：本波只做 py 后端；若走 gz 须先确认 `drone_vel_plugin`

8. **DeFoP 线暂缓**（用户裁决 2026-10-07）：CPN 的动作空间本身含偏航速率，
   与本节缺口不同源；未验证的部分**不写入本案卷**。

### 4.10 根因第二次定谳：**可用航程 = 墙钟 × RTF**，主凶是下视相机全程渲染（2026-10-08）

§4.7 把深度链的 RTF 从 0.661 救到 0.979 之后，10-08 复跑又掉回 **0.68–0.81**，
`landed_n` 恒 0、`full_completion` 恒 False。本节定谳：**同一个病从另一个节点复发**，
而 §4.6 的「预算=墙钟」正是它的放大器 ——
**RTF 不只是数据质量门，它是航程的直接乘数。**

#### 恒等式（十局逐位吻合）

| 环节 | 位置 | 事实 |
|---|---|---|
| 全局 `/use_sim_time` 只有 Gazebo 设 | `arena_world_gazebo/launch/gazebo.launch:17` | py 后端**从不设** ⇒ `rospy.get_time()` = 墙钟 |
| 任务计时器读 `get_time()` | `arena_mission/scripts/stage_controller_node.py:29,33,93` | `time_limit_s: 250` = **250 墙钟秒** |
| 世界按墙钟节奏推进 sim | `arena_world/scripts/world_node.py:319-322` `rospy.Rate(1/world_dt)` | 跟得上则 RTF=1；**RTF<1 = 掉步 = CPU 跟不上** |
| 观测窗到 DONE 早退 | `verify_run.py:177-180` | `wall_elapsed` 自 `wall_start` 起算 |

⇒ **无人机位移按仿真时间积分，任务计时器按墙钟走。可用飞行时间 = `wall_elapsed × RTF`。**

实测：`wall_elapsed` 恒 **267.6 ± 0.2 s**（= `time_limit_s` 250 + 17.6 收尾开销），
`sim_elapsed = 267.6 × RTF` 逐位成立：
`0.682→182.5 / 0.720→192.7 / 0.803→214.9 / 0.684→183.0 / 0.696→186.2 / 0.732→196.1 / 0.808→216.4`。

**落地数跟着仿真秒走**：266 s → 4 落地；216 s → 1；196 / 186 / 183 s → **0**。

#### RTF 是双峰的，且低态是常态

高态 `{0.994, 0.996, 0.996}`（局 3/4/5）vs 低态
`{0.682, 0.684, 0.696, 0.720, 0.732, 0.803, 0.808}`。
**最近八局里七局是低态** —— 高态才是「机器恰好空闲」的窗口。

低态**不是外部抢占、也不是节点集不同**：局#8 起跑时 WSL 全空
（loadavg 0.21、内存 283 Mi）仍只有 0.696；六局节点清单逐项相同
（47 节点，`camera_sim`/`depth_sim`/`depth_cloud` 各 12 个日志，`lidar` 0）。
局#8 逐核 `/proc/stat` 增量：8 核全部 90–95% user、**空闲增量恒 0**、
无 D 态、`io wait 0`、`%Cpu(s) … 0.2 id` ⇒ **纯 CPU 饱和**。
（9.7 GB / 9006 目录的 rosout 日志就此洗清嫌疑 —— io wait 为 0。）
宿主机侧实测 81%（20 逻辑核里 16 忙）。

#### 主凶 = `camera_sim`（下视彩色相机，诚实层）

`sensor.camera` 段（`sim_settings.yaml:758`）注释自陈：
**「唯一开关 = `competition_rules.color_id.source`，无独立 `enabled`」**
⇒ `source: camera` 一开就**全程**渲染。

#### 降帧率为什么安全（不是碰运气）

- `bucket_select.py:39` 是**逐调用计数**（`state["hit"] += 1`），调用者是
  `mission_executor` 的 20 Hz tick（取最新值、重复帧等值）
  ⇒ **`n_frames=3` 是「连续 3 个 tick 读到命中」，不是「3 张不同的图」**，
  锁定时序由 `scan_dwell_s` 决定、**与帧率完全解耦**。
- 唯一硬约束 = `color_detector_node.py:94` 看门狗：图像龄 > `stale_s=0.4 s`
  发 `NO_DET` 哨兵并把 hit 清零 ⇒ **fps 地板 = 2.5**。
  取 6 ⇒ 帧间隔 0.167 s，**2.4× 裕度**。
- **同族先例**：`sim_settings.yaml:778` 的 depth `15→7.5`（§4.7）
  就是同一味药治同一个病。
