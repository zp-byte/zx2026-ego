# ego 盲飞案卷（2026-10-06 定谳）

## 一句话

**`grid_map/pose_type` 配成 1，注释却写着「1=odom」——枚举实际是
`POSE_STAMPED=1, ODOMETRY=2`。** 于是深度-位姿同步器挂在
`/drone_<i>/planning/camera_pose`（全仓零发布者）上，`depthPoseCallback`
永不触发，**栅格图恒空，ego 自 Phase 1 起全程盲飞**。
「治理 ego 碰撞」第一轮三臂 A/B（E0/E1/E2）全部建立在一张空图上 ⇒ 对这一轮的
全部杠杆结论作废。

**后续四轮的分层定谳（详见 §九）**：空图已修（§三），但碰撞仍在，因为
**四个独立环节串联**——自桨幻影（§9.1-9.4，已修）→ 确认时延
（§9.7，`p_hit`，3+3 判 **pilot**：COLL −36% 但范围重叠）→ **冻结机制**
（§9.9c：单机 9 次碰撞即**本局永久停发**，六局 11 台到阈值/10 台冻结
⇒ 碰撞是**死刑判据**不是扣分项）→ **局部极小值**（§9.8：单点 goal +
无全局规划器，长于 horizon 的网墙即死锁，`p_hit` 完全不动它）。
**碰撞计数的历史口径全是错的**（§9.9a：编号逐机独立，`sort -u` 数的是最大逐机计数）。
**两条已试杠杆一条留一条毙**：`p_hit` 0.65→0.90 得 COLL −36%（但范围重叠 ⇒ **pilot 不翻默认**，§9.9b）；
**`max_vel` 2.0→1.0 判否**（COLL 反升 +51%、范围近分离，§9.9f）⇒ 碰撞对"时延"敏感、
对"速度"**反向**敏感，剩下唯一方向是**减少遭遇次数**（全局路由 / 抬感知视距），
而**停驻成因 ②（网前局部极小值）两条杠杆都不碰**。

## 七、碰撞机理定谳（全部实测，非推断）

工具：`~/ego_fleet_monitor.py`（每 10 s 全队测 深度率/成图率/位姿/**机心到最近膨胀格距离
`dmin_inf`**/点云规模 + 末帧 occ z 直方图）。两臂各 100 s 任务窗（H0=0.099，H1=0.45）。

**（1）栅格图里没有机身半径 —— 「看见了仍擦边」的精确机理**

| | 判据半径 | 膨胀给出的净空 | 结果 |
|---|---|---|---|
| 撞树判据（`gazebo_collision_monitor`） | 干轴外 **0.35 m** | — | — |
| 地图膨胀 `obstacles_inflation=0.099` | — | `ceil(0.099/0.1)=1` 格 = **0.1 m** | 规划器把机心送到干面外 **0.175 m** ⇒ **判据认定碰撞** |

实测坐实：H0 的 `dmin_inf` 常驻 **0.13–0.26 m**（正是贴着膨胀边界飞）。
**上游同源**：`advanced_param.xml`（仿真档）inflation=0.099、
**`advanced_param_exp.xml`（深度实飞档）=0.299** ——我们抄了仿真档，而它是"没有机身
半径"的档位。要保证不撞需 `ceil(inflation/0.1)*0.1 ≥ 0.35` ⇒ **≥ 4 格 = 0.4 m**。

**（2）地面占图 61%，膨胀后抬起"地板"，把机心吞进膨胀体 ⇒ 自囚**

occ 点云 z 直方图（n=20,983）：**z∈[-0.2,0.2) 有 12,758 点 = 61%**。相机水平前视
装在机体原点，巡航 2.4 m 时地面在 4.3 m 处进视场下沿（`z/tan(28.1°)`）。
地面被膨胀 5 格（0.45 ⇒ 0.5 m）后，**z<0.5 的整片空间成为膨胀障碍**：

| 臂 | `dmin_inf`（机心↔最近膨胀格） | 自囚（`dmin_inf < 膨胀半径`） |
|---|---|---|
| H0 inflation 0.099 | 0.13–0.26（> 0.1）| 否（d5 一度 0.060 踩线） |
| H1 inflation 0.45 | **0.018–0.069**（≪ 0.45）| **是，多机** |

H1 直接拍到自囚：d0 冻在 (10.35,-7.47,2.93) 二十秒不动、`dmin_inf=0.020`；
d5 冻在 (-23.1,4.3)、nInf 29,208。**自囚 = 规划器自己的起点在障碍里 ⇒ 任何重规划
都被 `bspline_optimizer.cpp:1243` 拒绝 ⇒ 无人机原地不动。**

**（3）自囚机最终会被推进树里**

H0（0.099）里 d5 从 t=30 s 起 `dmin_inf≈0.06` 卡在 (-23.15, 4.5–5.7, 1.27)（正是历史
头号热点树 (-23.2,3.8) 旁），**t=76 s 起连撞 5 次**。与 defop 侧"**低速贴树挤入**"
同型：卡在膨胀边界上的机最终被控制器推进树里。

**（4）感知节流是结构天花板（并列事实，非本轮病因）**

RGB+depth+point cloud，Gazebo Classic 用 Ogre 软渲染，6 机 × 15 Hz 的渲染需求供不上。

## 九、第三轮定谳：无人机把自己的桨画进了栅格图（自桨幻影）

**这是 §七 那个「自囚」的真身，也是 H0/H1/H3 三臂全部读数被污染的原因。**

### 9.1 几何事实（源码可复算）

`world_builder.py:356-364` 的机体视觉：桨叶 = `<cylinder><radius>0.10</radius>`，
中心在 `tx,ty = dx*0.24, dy*0.24`（即 (±0.24, ±0.24)）、`z=+0.062`；机臂 = 长 0.24 的盒。
D435 插件 `clip.near = 0.30`、`horizontal_fov = 1.5184`（半视场 43.5°）、
`fy = 134.9`（半视场竖 28.1°）。

`drone_depth_sensor()` 的原注释写：

> 装机体系原点平视（pose 全 0）：own visuals 最大前伸=机臂尖 0.12+桨 0.10=0.22
> < near clip 0.30 ⇒ **自遮挡免疫**

**两处都错**：
1. 把机臂**半长** 0.12 当成臂尖。桨盘中心其实在 (±0.24,±0.24)，**外缘伸到 0.44 m**。
2. **near clip 只裁掉比它「近」的几何；比它「远」的照渲染**——"小于 clip" ≠ "不可见"。

### 9.7 第四个独立环节：**确认时延**——视距是名义的，确认要 6 帧（新定谳）

§五 把 horizon 当"量程"问题（4.5 m 看不远）。但**量程 ≠ 可用量程**：栅格图把一个
体素判成"占据"需要的不是 1 帧，而是**一串命中**。

**代码事实**（`grid_map.cpp:485-508`，`updateOccupancyCallback`）：缓存队列里的每个
体素**每帧恰好消费一次**，随后计数立即清零：

```cpp
double log_odds_update =
    md_.count_hit_[idx_ctns] >= md_.count_hit_and_miss_[idx_ctns] - md_.count_hit_[idx_ctns]
        ? mp_.prob_hit_log_ : mp_.prob_miss_log_;
md_.count_hit_[idx_ctns] = md_.count_hit_and_miss_[idx_ctns] = 0;
...
md_.occupancy_buffer_[idx_ctns] =
    std::min(std::max(md_.occupancy_buffer_[idx_ctns] + log_odds_update, mp_.clamp_min_log_),
             mp_.clamp_max_log_);
```

⇒ 一格的行程 = `logit(p_min) → logit(p_occ)` = `logit(0.12) → logit(0.80)`
= `−1.992 → +1.386` = **3.378**。每帧只能加 `logit(p_hit)`：

| p_hit | 每帧 log-odds | 需帧数 | @2.80 Hz（本轮实测） | 1.33 m/s 下行程 |
|---|---|---|---|---|
| **0.65（母本）** | +0.619 | **6 帧** | **2.14 s** | **2.85 m** |
| 0.90 | +2.197 | **2 帧** | 0.71 s | 0.95 m |

**融合帧率 = 深度帧率（2.80 Hz）**——已实测并源码确认：`updateOccupancyCallback`
挂在 **0.05 s(20 Hz)** 定时器上（`grid_map.cpp:133`），但进门先查 `occ_need_update_`，
而该标志只由深度回调（`depthOdomCallback`）置位 ⇒ 20 Hz 定时器被降频到深度率。
`projectDepthImage() → raycastProcess()（内含融合）→ clearAndInflateLocalMap()`
一串都在这一个回调里。

> **陷阱（防误读）**：`grid_map/occupancy` 与 `occupancy_inflate` 的**发布率实测 7.44 Hz**
> ≠ 融合率。那是 `visCallback`（`grid_map.cpp:134`，0.11 s = 9.09 Hz）**无条件**
> 发两次当前缓冲，与是否融合无关。指纹 = **两话题条数逐字相同**（实测 186/186）。
> 拿发布率当融合率会把 6 帧时延算成 0.8 s（低估 2.6×）。

**可用量程 = 视距 − 确认行程 = 4.5 − 2.85 = 1.65 m**（p_hit 0.90 档 = 4.5 − 0.95 = **3.55 m**，
2.2×），而
`manager/planning_horizon = 7.5 m` ⇒ 规划器**在"尚未确认"的空间里规划**，
把机领进树干。这与 §9.5 的形态学吻合：**不是"飞进树里"，是"顶住树干"**——
计划在撞点前后才第一次看见障碍，刹车距离（0.8 m/s² 级 + 0.5 s 反应 ≈ 1 m）不够。

**顺带订正 §五 的一个死键**：`grid_map/local_update_range_{x,y}` 是
`ray_length + 1.0 = 5.5`、`z = 4.5`，都 **> 4.5 m 视距** ⇒ `updateOccupancyCallback`
里那段 `if (!in_local) occupancy_buffer_ = clamp_min_log_` 的"窗外擦除"在
本配置下是**死代码**（被射线触及的体素必然在窗内）。真正的 horizon **只有
`max_ray_length` 一个**，不是三件套（原 §五 的"三件套须一并抬"说法收窄）。

**杠杆 = `p_hit`（新 launch arg，默认 0.65 = 母本 = 零行为变更）**，
四层穿透 `gazebo.launch → stack_nodes.launch → ego.launch → advanced_param_zx.xml`，
落点 `advanced_param_zx.xml:114`。选 0.90 不选 0.97 的理由：0.967 以上才降到 1 帧，
而**单帧即判占据会吃掉全部噪声抑制**（深度边缘的混合像素会立刻变成幻影墙——
本项目已有幻影墙病史），0.90 保留"两帧一致"这一层冗余。

**A/B（`~/ego_phit_ab.sh`，跑中）**：R0 `p_hit 0.65` / R1 `p_hit 0.90`，

#### (c) 冻结机制（新定谳：把"碰撞"与"任务死"直接连起来）

`gazebo_collision_monitor.py:224-241`：

```python
if st["freeze"]:  self.pub_vel[i].publish(Twist());  continue   # 每拍发零速
...
if hit and st["t"] < 0:                 # 新碰撞
    st["count"] += 1
    if st["count"] > self.max_collisions:     # 默认 8
        st["freeze"] = True                   # ⇒ 本局**永久**停发
        rospy.logerr("... drone %d frozen (>max_collisions=%d)", ...)
        continue                              # ← 第 9 次**不落 COLLISION 行**
```

⇒ 两条推论，本轮实测全部吻合：

1. **逐机计数里每个 `#8` 都是一台"骑在门槛上"的机**：第 9 次撞击不写 COLLISION
   行而写 `frozen` 行 ⇒ 冻结机的最大 `#N` **恰为 8**。
2. **六局实测 11 台机达到 `#8`，其中 10 台冻结**（R0#1 2/2、R0#2 3/3、R0#3 2/2、
   R1#1 1/1、R1#2 3/2、R1#3 0/0）。⇒ **冻结几乎是到达阈值的必然结局**。
3. **冻结 = 该机本局彻底不动**（每拍零速，无恢复分支）⇒ 停驻、无法投放、无法返航、
   无法落地。`max_collisions` 在 `sim_settings.yaml:688` 是 R1 时代从 3→5→8 调上来的
   场景侧故障注入参数，**不属可动杠杆**（动它=改判据）。

⇒ **碰撞在本题里不是"扣分项"，是"死刑判据"**：单机 9 次碰撞即换一台机退出任务。
这把 §9.8 的"六机跑不完"与碰撞**因果闭环**了——冻结机数 2.33/run 直接解释
了大部分停驻与 0–2/6 的落地率。

#### (d) 停驻的两个成因（必须分开，本轮的"停驻协变项"）

把冻结机名单与位置踪迹逐台对质，停驻有**两个独立来源**：

| 成因 | 判据 | 例（R1#1） |
|---|---|---|
| **① 冻结** | 该机在冻结名单里 | d1 钉在 (−18.52,−3.41,2.49) 115 s；其 8 撞跨 sim 32–159，第 9 撞≈sim 159 ⇒ 冻结即停 |
| **② 局部极小值** | 不在冻结名单，却长时间不动 | d4 钉在网西面 (−23.16,4.98,0.58) **210 s**，全程**仅 1 次碰撞**；d2 钉在 (26.91,8.76,0.80) 155 s，仅 2 次碰撞 |

⇒ **② 才是 §9.8 已定谳的"网前局部极小值"**（无全局规划器），
**① 是本轮新增的、由碰撞触发的**。p_hit 只动 ①（2.33→1.00），
**完全不动 ②** ⇒ 故总停驻机数没降（4.0→5.7 的上升是 ② 的局间方差）。

#### (e) 刀刃算术：为什么 2.0 m/s 是结构性地盲飞

`§9.7` 的确认时延给出一个**闭式临界速度**：

```
v_crit = 视距 / 确认耗时
```

| 档 | 确认帧数 | 确认耗时 | v_crit @视距 4.5 m |
|---|---|---|---|
| p_hit 0.65（母本） | 6 | 2.14 s | **2.10 m/s** |
| p_hit 0.90 | 2 | 0.71 s | **6.30 m/s** |

而 `ego.launch:15` 的 `max_vel` 默认 **2.0**（"对齐 competition_rules max_vel"），
`R0#3` 报告里实测 `max_speed = 1.823` ⇒

- **可用预警距离** = 4.5 − 2.14×1.823 = **0.60 m**（@2.0 m/s 时只剩 **0.21 m**），
- 而**机身半径 0.35 m** ⇒ **预警距离 < 自身体宽**。

⇒ 母本配置下 ego **恰骑在刀刃上**：障碍必须在 4.5 m 内**被连续照射满 2.14 s**
才进图，超速即"永远认不出来"。这解释了为什么 §9.7 的四层穿透全过后
碰撞只是**降**而不是**消**——p_hit 把刀刃从 2.10 挪到 6.30 m/s（刀刃消失），
这是本轮 COLL −36% 的**唯一**机理来源，但局部极小值(② / §9.8)不受其影响。

#### (f) 速度臂定谳：**降速是明确的回归**（`~/ego_vel_ab.sh`，V1 ×3）

在 R1（p_hit 0.90 / 2.0 m/s）之上**单变量**把 `max_vel` 降到 1.0：

| 臂 | COLL 均值 [范围] | 簇 | ctl_pts | landed | **冻结机/run** | 停驻机/run |
|---|---|---|---|---|---|---|
| R0 = 0.65 / 2.0 | 31.0 [25,39] | 20.3 | 146050 | 1/18 | 2.33 | 4.0 |
| **R1 = 0.90 / 2.0** | **19.7 [13,28]** | 12.7 | 70337 | 2/18 | **1.00** | 5.7 |
| **V1 = 0.90 / 1.0** | **29.7 [28,31]** | 15.7 | 45687 | 2/18 | 1.67 | 1.3 |

**判：降速判否，速度杠杆关闭。** 理由：

- COLL **+51%**（19.7→29.7），且**范围近于分离**——V1 `[28,31]` 极紧，与 R1 `[13,28]`
  仅在端点 28 相接；这是全部三轮 A/B 里**最干净的一次分离**（比 p_hit 那次干净得多）。
- 簇 12.7→15.7、**冻结机 1.00→1.67**（比 2.0 m/s 更容易撞到死刑线），`landed` 不变。
- **(e) 的算术没错，但选错了杠杆**：预警距离确实随速度变长，可碰撞不是"来不及看见"，
  而是**"看见了仍被挤住"**——降速只是把同一段接触**拉长**。
  ⇒ 这是本项目**第三次**独立复现同一条教训（`dam v2` 挤入减速、`③ 监督层` 禁再减速），
  这次在 ego 臂上：**「低速贴树挤入」形态下，减速=延长暴露=更多碰撞**。

⇒ 两条杠杆合起来给出一个反直觉的**对消**：把 p_hit 提到 0.90 赚到的 −36%，
在 1.0 m/s 下**被完全吃掉**（V1 ≈ R0 的 29.7 vs 31.0）。
**碰撞数对"时延"敏感、对"速度"反向敏感** ⇒ 剩下的只能是**减少遭遇次数**：
让机**不走**那条必经树列的路线（全局规划 / 路由），或让**树在承诺点之前就进图**
（`ray_length` 感知视距，§9.7 已定谳本配置下令 horizon 只有 `max_ray_length` 一项）。

#### 结论：三层主次

1. **主因 = 路线层。** `_goto()` 单点 goal（无路点序列）+ ego 无全局规划器 ⇒
   局部 B 样条在 `planning_horizon 7.5` 上优化，而**可用量程只有 1.65–3.55 m**
   ⇒ 在"尚未确认"的空间里选线，选出一条**穿过树干列**的线。
   **这一层解释了 (2) 的全部读数**，也解释了为什么降速（延长暴露）与
   p_hit（只把确认提前）都**只能改次数、不能改集合**。
2. **放大器 = 脱困失败。** 首次接触后 ego 出不来，磨树把计数放大 ~1.65×。
3. **死刑 = 冻结**（§9.9c）：累计 9 撞本局永久停发。

⇒ **杠杆必须作用在第 1 层（改路线）**，不是继续调确认时延或速度。
两条候选见 §十一「未试的杠杆」。

#### 9.18.4 关键订正：`lock_cmd` 在 Gazebo 后端**根本不存在**

§9.18 原方案曾断言「桥的 `SETTLE_S` 零速段在物理上被监控器整个吞掉（`lock_cmd`
丢弃桥的令），故 `SETTLE_S` 只是冗余保险」。**这条是错的**：

- `lock_cmd` 的**唯一**实现是 python 后端 `arena_world/scripts/world_node.py:157-161`
  （消费端 `_on_vel_cmd` **丢弃** vel_cmd）。
- Gazebo 后端的消费端是 C++ 插件 `drone_vel_plugin`（改不得），
  `gazebo_collision_monitor.py` **从不读** `enabled`/`lock_cmd`（`grep -n enabled`
  零输出）。
- `sim_settings.yaml` 上 `lock_cmd` 自己的注释就写明过这个失效模式（run4/5 法证：
  「否则 20Hz 指令流逐拍覆盖恢复指令，架空冻结→着地机被 hover 回拉持续压入地下，
  d1 沉至 z=-3.56」）。

⇒ 在 Gazebo 后端上桥的零令**是活的**，而且它**正是 R1 的成因**。原方案把
「已失效的锁」当成「已生效的锁」来推理，方向反了。

#### 9.18.5 修复：恢复期让出执行器（`yield_actuator`）

把 python 后端的 `lock_cmd` 语义**在生产端**镜像：恢复窗内桥 `pub_raw`
**整窗不发任何令（含零）**，`/vel_cmd` 归 `gazebo_collision_monitor` 独占
（弹开 100 Hz → 冷却零速）。

| 决策 | 理由 |
|---|---|
| **边沿自同步**（上升沿让出 / 下降沿交还），不镜像 `bounce_dt/cooldown_dt` | 窗口算术是外部约束的镜像，改一个忘一个就错位；边沿即真值 |
| **必须是静默而非发零** | 发零就是与弹开令对撞的那个写者 |
| **dbg 心跳继续发** | 它是 nav stall 看门狗（`pen_stall_freeze_t=1.0`）的**唯一**输入；心跳一停 nav 主循环改发 `Twist()` 零速 = 换个写者继续掐弹开。本窗实测 2.5 s > 1.0 s 阈值 ⇒ 不喂必每窗触发 |
| **看门狗 `YIELD_MAX_S=15`** | 监控器若死则永远收不到下降沿 ⇒ 防永久静默（正常窗 2.5 s，留 6× 裕度） |
| 落在 `ego_bridge_node.py`（ego 专用） | 零共享文件风险（本仓强纪律） |

- 代码：`src/ego_zx/scripts/ego_bridge_node.py`（`_on_collision` 边沿机 + `_tick`

② 撞点是 0–6 cm 擦入（撞点距中位 0.49 m vs 判据 0.50 m），慢速下控制误差的绝对

机会增多」。⇒ 本批不预设结论。

**预登记判据**（n=3，看均值，禁单判）：① Σcol 均值 ≤14 命中 / 14–18.5 方向性

### 9.19 速度 A/B 首跑全废 + 批有效性闸门（2026-10-07）

§9.18 修完 `yield_actuator` 后**立即**起速度 A/B，**第一局就全废**。本节记的
是「为什么废」以及**它暴露的流程缺陷**——缺陷不在配置、不在代码，在**跑器**。

#### 9.19.1 退化表象，以及它有多像一个真结论

`S2_1`（`max_vel=2.0`，即**基线臂**）读数：`COLLISION=0`、`frozen=0`、
`LANDED=0`、`PT=15`（历史常值 8–13 的同量级，基线 167–171）、`s1=0/verdict=none`、
四台机钉在西侧 `x≈−25…−28.5` 不越网。

**危险处在于它长得很像结论**：「基线臂零碰撞零落地、四机不过网」读起来完全
可以解释成「这一代栈在 2.0 m/s 下瘫了」甚至「1.0 那臂反而会更好」。若照原判据
走完 6 局，会得到一份**方向可能完全反的判决**，而且每一步都「有数据支撑」。

#### 9.19.2 闸门：RTF = Δsim/Δwall

**判据**：`ego_rtf.py`，从 roslaunch 日志里的 `[<wall_epoch>, <sim>]` 对算实时因子。

| 语料 | RTF |
|---|---|
| 批 2 干净 12 局（`/tmp/ego_collfix6`） | **0.820–0.843**（极紧，跨臂无差） |
| 首跑污染局 `S2_1` / `S1_1` | **0.524 / 0.547** |

两档无重叠 ⇒ 阈 **0.75** 有充裕裕度。三条取数口径（都是踩过的坑）：
① **必须过滤 `sim>0`**：gzserver 起钟前的行全是 `sim=0.000000`（单局里 1.8 万行
日志绝大多数是 0），混进来把 Δsim 压扁、RTF 假低；
② **按 sim 取最小/最大两条**，不是日志首尾行——多节点并发写，行的 wall 顺序与
sim 顺序不一致；
③ 窗口须 ≥30 s 仿真，否则调度抖动主导读数。

**RTF 为什么是闸门而不是参考读数**：ROS 节点走**墙钟**、gazebo 走**仿真钟**，
两者比值一变 ⇒ 每仿真秒的控制拍数就变 ⇒ 动力学**真的**变了。它是对撞 A/B 的
**混杂因子**，不是无关的环境读数。故判据 ⓪ 先于其余所有判据。

跑器内两道门：**90 s 中途门**（<0.65 即停，省掉整局）与**局末门**（<0.75 即作废
停批），逐局 RTF 写进 `summary.txt` 留证。**中途门当天就开火了**（下一小节）。

#### 9.19.3 抢占源定谳：横跨 WSL 边界的一条工作负载，不是孤儿

`load average 46.07`（8 核）。起初怀疑是「本批被 TaskStop 掐掉后的残留 ROS 节点」
（历史真事），**实测证伪**：`pgrep` 三个名字全空、45 s 密集采样零 gzserver。
真凶是**宿主机上另一条线在飞的工作**，横跨 WSL 边界的一半各占一边：

| 侧 | 进程 | 实测占用 |
|---|---|---|
| Windows | `python.exe` → `bridge/isaac_sim_server.py --driver isaac --scene dense_spruce` | ~3.1 核 |
| Windows | `Code`（VS Code） | ~1.6 核 |
| WSL | `evaluate.py` | 126 % |
| WSL | `vae_node.py` / `img_filler.py` / `isaac_ros_bridge.py` | 合计 ~1.3 核 |

**一条工作负载同时吃两侧 CPU**（Isaac Sim 服务端在 Windows 原生跑，其 ROS 半边
在 WSL），这解释了为什么「WSL 侧只剩 1.2 核空闲」却仍跑不动：8 逻辑处理器里被
Windows 侧瓜分掉大半，WSL 的 8 vCPU 是**超订**的。

**处置：一根毫毛没碰。** 它日志在持续增长（`evaluate.log` 每 12 s +15 KB），是活的、
在产出的跑；杀掉它 = 破坏用户另一条线的工作。**它的 ROS master 已死**这件事只作
情报上报（`roscore.log` 末尾 `shutting down`，三个 ROS 进程名字挂 `CLOSE-WAIT → 11311`，
靠自有 socket 协议 `bridge/protocol.py` 继续产出）——**是不是预期形态，由用户判断**。

#### 9.19.4 跨栈卫生三改：清场必须按**归属**，不能按**名字**

发现抢占源之后，跑器原有的清场逻辑从「本机独占」的假设变成了**会伤人的动作**。
三处改，每处都写明它的**失败模式**：

| # | 旧写法 | 改法 | 不改的后果 |
|---|---|---|---|
| 1 | `ROS_MASTER_URI=:11311` | **`:11411`** | 对方的 `ROS_MASTER_URI` 也是 11311，我一开 master 就可能被它那几个挂着 `CLOSE-WAIT` 重试的 ROS 进程挂上（`img_filler` 发深度图、bridge 发 odom/cmd）⇒ **整批串话题**。本仓既有先例：arena 并行跑用 11411 |
| 2 | `pkill -x rosmaster` | **按本端口点名 PID**（`ss -ltnp` 取 `pid=`） | 对方有 `roscore_probe.log` ⇒ 会重试起自己的 master；按名杀会**连它一起杀掉** |
| 3 | `pkill -x gzserver` | **白名单**：只认 cmdline 含 `zx2026_ego_ws` 的 | 实测对方会**短暂**起 gzserver（45 s 采样抓到一次瞬时进程）；按名杀会误杀 |

已核：`src/` 内**无 11311 硬编码**、无脚本覆写 `ROS_MASTER_URI`；自家 gzserver 的
cmdline 实测为 `/bin/sh …/gzserver /home/ubuntu/zx2026_ego_ws/src/arena_world_gazebo/
worlds/forest_world.world` ⇒ 白名单令牌在自家路径里，两边不交叠。

**改法 3 的失败模式是「响亮」的**（这是选白名单而不是黑名单的理由）：白名单若失配，
我自己的 gzserver 会被 `dirty()` 报成残留 ⇒ `settle_clean` 直接 ABORT 停批，
**不会**静默污染下一局。这比误杀别人的活跑好。

#### 9.19.5 四件仪器的离线对质（先证器，再烧批）

| 仪器 | 对质方式 | 结果 |
|---|---|---|
| `ego_rtf.py` 闸门判定 | 12 局真值 + 缺文件 + 窗口过大，共 6 例比对期望退出码 | **6/6 PASS** |
| `master_pid`/`dirty` | 抽**真源码函数块** + 真监听者（loopback 裸 socket） | **ALLOK**（空→不报；有→点名正确 pid） |
| `my_gz_pids`/`kill_my_gz` | 造两个真 `gzserver` 进程（`cat <fifo>` 阻塞保活），一个带自家路径、一个带外来路径 | **ALLOK**（自家被杀 exit −15、外来存活） |
| 中途门端到端 | 真起批 | **开火**：90 s 窗口 `RTF=0.621` ⇒ 12:46 起、12:48 自停 |

**自停的价值**：首跑烧掉 **37 分钟**才发现全废；这次 **~2 分钟**就停。清场已验证
干净（`CLEAN OK (escalated)`，`roslaunch`/`gzserver`/11411/跑器全空）。

#### 9.19.6 当前状态与判据变更

**用户裁决**（2026-10-07）：**等宿主空闲后自动起批**。守护 `~/ego_speed_watch.sh`
每 180 s 探两侧（Windows：Name 过滤的 `.ps1` 数 `isaac_sim_server`；WSL：
`ps|grep` 括号法数进程 + `load1<2.5`），空闲即起批；**每次重试用全新 `_attN`
输出目录**（否则上一轮残局日志会被汇总判官按 tag 当成本轮数据读进去——首跑污染局
的 `S2_1.log` 就差一点被当成本批数据），成功后写 `_OK` 指针。上限 5 h。

**判据变更**：新增 **⓪ RTF ≥0.75**（先于一切）。原判据 ①–⑦ 不动。刻意**不**把
RTF 当「已排除」的脚注：批 2 的 `Σcol 18.5` 基线是在 RTF≈0.83 下测的，本批若在
别的 RTF 下跑出来，① ④ 的**可对质性**本身就要重新论证。

**RTF 与可对质性的判定规则（先于数据登记，不可事后更改）**：

| 本批 RTF 带 | 判据 ①（Σcol ≤14）④（越网 ≥16/18） | 其余 |
|---|---|---|
| 落在批 2 基线 **0.820–0.843** 内 | **可直接对质**，照原判据 | 照常 |
| 落在 **0.75–0.82** | **降级为指示性**：必须报出 RTF 带，并声明「Σcol 之差含 RTF 混杂，**不是**干净单变量」 | ⓪②③⑤⑥⑦ 仍为硬判据 |
| < 0.75 | 局作废、停批（闸门），**不进判定** | — |

**不接受任何「先看结果、再决定 RTF 怎么算」的处置**——那正是预登记要防的东西。
理由：批 2 基线本身是 RTF≈0.83 下的乘积，拿 0.78 下的读数去比 ① 的 14/18.5 阈值，
差的可能全是 RTF 而不是 `max_vel`。

#### 9.19.7 诚实边界

1. **闸门只证「宿主够快」，不证「配置对」**——它不替代 `verify_cfg`，也不替代
   判据 ①–⑦。
2. **阈 0.75 来自 12 局两臂语料**，不是理论值；语料变了该重测（本器价值在**方法**：
   真值分离 + 中途早停，不在那个数）。
3. **RTF 与碰撞的定量关系未测**：只知道 RTF 0.52 时任务**根本没跑完**（335 s 窗口
   只推进 185 s 仿真，而任务需 ~290 s），所以低 RTF 的失效**首先是任务不完成**，
   不是「碰撞变少」。中间档（0.75–0.82）的行为**未知**，故阈取在 0.75 而非「贴住
   0.82」以留裕度，但这一档若有系统性偏置，本批也测不出来。
4. **守护的探活是近似的**：`load1` 是 EWMA，且 Windows 侧只看 `isaac_sim_server`
   一个模式——别的 Windows 重负载（另一次 Isaac、另一次编译）**不在判据内**。
   真正的兜底仍是跑器自己的两道 RTF 门。
5. **未被本流程覆盖的旧隐患**：`cleanup` 只认 gzserver/roslaunch/master 三类残留，
   历史「396 孤儿」里的 python 节点类（`nav_node`/`depth_sim`/planner）**不在点名
   范围**。本轮实测无此类残留（`ps` 全扫为空），但**不是跑器保证了这一点**。

### 9.21 换场当天翻车：叶 mesh 把 ego 的深度相机压死（2026-10-07）

### 9.22 深度超时标志**永久闭锁**，且 RTF 闸门抓不到它（2026-10-07，S2_3 法证）

**现象**：速度 A/B 第 5 局 `S2_3` 一次性 `Depth Lost! EMERGENCY_STOP` **27511** 行，
六机自 sim ≈49 s 起**钉在完全相同的位姿**直到收局（pos.txt 末行坐标数分钟不变）。
但它长得**像一局健康局**：`COLLISION=4`、`frozen=0`、**`RTF=0.805`（过了判据⓪ 0.75）**、
`landed=0`。**跑器把它当有效局收了。**

**死因（读源码 + 实测，非推断）**：

1. `grid_map.cpp:673` 的门是 `(ros::Time::now() - md_.last_occ_update_time_) > 1.0`，
   而 `use_sim_time=true`（`gazebo.launch:10`）⇒ **两个钟都是仿真时间**，
   所以**单纯的 RTF 掉速不会点着它**（两个钟一起慢）。门比的是
   「仿真钟 vs **该节点真正消费掉一帧**的仿真时刻」——是**消费者侧**的指标。
2. `last_occ_update_time_` **只在 `occ_need_update_` 为真时刷新**（即真的处理了一对
   synced depth+odom），定时器本身是 `ros::Duration(0.05)`（20 仿真 Hz）。
3. **`flag_depth_odom_timeout_` 置 true 后全仓无复位点**：`grep` 只有
   `grid_map.cpp:151`（构造函数里 `=false`）与 `:677`（`=true`）。⇒
   `getOdomDepthTimeout()` **此后恒真**，`ego_replan_fsm.cpp:684`
   每一拍都 `changeFSMExecState(EMERGENCY_STOP)` ⇒ **一次瞬时抖动 = 整局判死**。
4. 实测那一次抖动的形状：**六台机在 wall 同一毫秒（1791357698.949）、sim 同一时刻
   （49.000）同时报错**，`now - last_occ_update` = **1.45 / 1.45 / 1.45 / 1.90 / 2.34 / 2.36**
   仿真秒（六机各自的 last 值 47.55 / 47.55 / 47.55 / 47.10 / 46.66 / 46.66）。
   **是一次全局瞬时事件，不是速率退化。**

**⚠ 同时订正一处仪器问题**：深度「帧率」我此前一律引用 `rostopic hz`
（各局 2.37–2.75 Hz；有叶档 0.595）。**那是订阅端的数字，不是传感器的时率**。
`/tmp/gap.py` 直接读 `msg.header.stamp`（这才是门的输入）实测**同一话题同期**：
**帧间隔中位 0.086 仿真秒（≈11.6 仿真 Hz）、最大 0.502 仿真秒、越过 1.0 s 的 0 帧**；
而同一冻结状态下 `rostopic hz` 只报 1.865 Hz —— **两台仪器差 2.6 倍**。
倾向信 header.stamp 版（大 buffer、直接读帧自带戳），但**这是待查的仪器分歧，不当噪声抹掉**。
**它不影响因果结论**（有叶档确实点着了 11966 条 EMERGENCY_STOP，抽稀后四局归零），
但**所有以"Hz"记的绝对裕度数都要降级为「仪器相关」，除非改用 header.stamp 版复量**。

**新纪律（判据层）**：**`Depth Lost` 计数必须独立成门，不能只靠 RTF**。
本局 `RTF=0.805` 完全合格 —— 与 §9.21 的叶事故**同一副假签名**
（RTF 正常 / col 接近 0 / landed 0）。凡见三件套同时出现，先数 `Depth Lost`。

**未做**：① 没有验证「sim 49 s 那一次抖动的物理成因」（是否与任务起飞、模型插入、
gzserver 渲染线程一次长停顿有关）——只知道它是全局瞬时的；② 没有复现过第 2 次。
